HOW TO USE DAVINCI ARCHITECT

This guide explains the pipeline, the configuration selector, the AI provider selector, the API key manager, the metrics on the results page, and the two PDF reports.

1. WHAT THE PIPELINE DOES

DAVINCI converts a system description into a microservice architecture. Each system is described by a name, an architecture target, functional requirements, reference services, and reference interactions. The reference lists are used only to score the generated architecture; they are not given to the language model as an answer key.

The pipeline is a sequence of agents. Every agent receives the previous artifact and returns a new one, so the final architecture is the product of the whole chain, not of a single prompt.

AGENT 1

Initial proposal

Reads the requirements and produces the first service and interaction decomposition.

AGENT 2

Second proposal

Produces an independent second decomposition from the same requirements.

AGENT 2.1

Generalist second proposal

Replaces Agent 2 in C4. It uses the same prompt as Agent 1 with a different example.

AGENT 4

Refinement

Reviews and improves a proposal before it is consolidated or exported.

AGENT 3

Consolidation

Compares two proposals and produces the consolidated architecture.

AGENT 5

Specification

Writes the final architecture as a YAML specification.

2. PIPELINE CONFIGURATIONS (C0 TO C5)

The configuration selector on the main page, and on the results page, defines which agents run. The default is C1. Every option uses the same models and the same input fields; only the chain changes.

OPTIONAGENTS EXECUTEDWHAT CHANGESWHEN TO USE IT
C01One proposal. No second proposal, no refinement, no consolidation, no YAML stage.A quick baseline of the first agent.
C11, 2, 4, 3, 5Two proposals, refinement, consolidation, and the YAML specification. This is the reference configuration.Normal use and the comparison baseline for the experiment.
C21, 2, 3, 5The complete pipeline without Agent 4, which isolates the contribution of refinement.Measuring what refinement adds.
C31, 4, 5One proposal is refined and exported; Agents 2 and 3 are removed together.A single refined architecture, at lower cost.
C41, 2.1, 4, 3, 5Agent 2 is replaced by Agent 2.1, a generalist with Agent 1's prompt and a different example.Testing whether the second proposal depends on a specialized prompt.
C51, 2, 4, 3, 5, with 3 twiceControl condition for Agent 3. Without a frozen run directory it regenerates the proposals like C1 and runs Agent 3 twice.Control runs only. It costs more than C1 because the second Agent 3 pass is added.

C5 is a control condition, not a faster or better option. Because it regenerates the proposals before the second consolidation pass, a C5 run takes longer and consumes more tokens than C1.

3. AI PROVIDERS AND MODELS

The AI provider selector defines which model family executes the agents. The model is fixed per provider, so the same configuration is comparable across runs.

Only the selected provider is used. Providers that are not selected stay inert, so a key that is inactive or expired for another provider does not affect the run.

If the selected provider has no key, the interface blocks the run with a message. This avoids starting a request that would fail at the first language model call.

4. HOW A SELECTION IS CONFIRMED

The configuration and the AI provider use the same interaction. The selector opens an in-page menu; the page is not reloaded, so anything already typed into the system form is preserved.

  1. Click the selector to open the menu.
  2. Click an option. The choice stays pending, and the menu remains open.
  3. Click outside the menu to finish. A popup asks you to confirm or discard the change.
  4. CONFIRM saves the choice on the server and applies it. DISCARD restores the previous value.

Until the popup is confirmed, nothing is saved and no run uses the pending value. The configuration is not reset by a completed run, by NEW DECOMPOSITION, or by a page reload.

Both values are stored on the server, so they are the same in another browser tab or after a server restart. The browser does not store them in local storage.

RUN AGAIN uses the configuration and provider active at the moment of the click. If the selector has an unconfirmed change, the interface asks for confirmation before starting.

5. API KEYS

Where keys are stored

All keys live in one file, Experimento_Multiagente/.env, which is ignored by Git. The interface settings file, Interface/settings.json, stores only the active configuration, the active provider, and the active key number for each provider. It never stores a key value.

Numbering and activation

Each provider has its own sequence. The key that already exists becomes Key 1; new keys become Key 2, Key 3, and so on. Adding a key never deletes the previous one. The previous key remains in the file as an inactive, commented line with its provider and number.

Only one key per provider is active at a time. The active line is the one the pipeline reads. Selecting another key rewrites that line and comments the previous one.

Adding a key

  1. Open the AI provider menu and select the provider.
  2. Paste the key into the password field. The value is not sent anywhere until you click SAVE KEY.
  3. Leave Set as the active key for this AI unchecked to register the key without activating it. Check it to make the new key active immediately.
  4. Click SAVE KEY. The field is cleared, and the provider then lists the new key by label only.

If a provider has more than one key, choosing that provider also requires choosing the key. The choice is stored per provider, and the provider and key are confirmed together by the same popup.

What the browser receives

The browser receives labels only, such as Key 1 and Key 2, and whether the provider is configured. No key value is returned by the server, written into the page, or stored in the browser after saving. The input is a password field and is cleared after every save attempt, successful or not.

Declared limitation. While you type, the value exists in the password field, and at the instant you click SAVE KEY it travels in the request body, where it is visible in the browser developer tools. After the response, no key value remains in the page, in local storage, in cookies, or in any response. The server does not log the request body.

6. RUNNING THE PIPELINE

Fill in every required field for each system, then click RUN PIPELINE. Up to ten systems can be submitted in one run. The form accepts one system definition per block, and REMOVE deletes a block while at least one remains.

During the run, the progress bar advances slowly and continuously. It accelerates when a system completes and stops before 100 percent until the final response arrives. The status line reports how many systems have been completed, the total, and the system currently being processed. The selectors are disabled while the run is in progress.

When the run finishes, the results page shows the metrics and a summary line with the configuration and the AI used, for example Run configuration: C1 | AI: DeepSeek (deepseek-chat).

7. RESULTS AND METRICS

The results page has three sections. Services and interactions compare the generated architecture against the reference lists provided in the form. Best results show, per system, the highest-scoring services and interactions.

COLUMNMEANING
SystemThe system name from the form.
ProposalWhich proposal of the run produced the value.
PrecisionShare of generated items that match a reference item.
RecallShare of reference items that the generated architecture covers.
F1-scoreHarmonic mean of precision and recall.

Warnings and errors are listed above the tables. A system that fails does not prevent the other systems in the same run from being reported.

8. PDF REPORTS

Two reports are available on the results page.

Download full report (PDF)

Contains the system definitions, the proposals, the metrics, and the best results. The header prints the configuration and the AI with its model. Each system block repeats the configuration that produced it.

Download YAML specification (PDF)

Contains the architectural specification produced by Agent 5, with the same configuration and AI fields in the header and in each block.

A run restored from disk after a server restart reads a small metadata file written into the run directory. If that file predates the metadata feature, the report prints not recorded instead of inventing a value. No key value appears in either report.

9. TROUBLESHOOTING

The run is blocked because the provider has no key

Open the AI provider menu, select that provider, paste a key, and click SAVE KEY. You can also choose another provider that is already configured.

The selection did not change

A selector change is applied only after CONFIRM in the popup. If you clicked DISCARD or pressed Escape, the previous value is restored.

The reports show "not recorded"

The run was produced before the metadata file existed, or the file was removed from the run directory. The architecture and metrics are still valid; only the configuration and AI fields are missing.

The server does not start

Start it from the repository root with the project virtual environment active:

python Interface/server.py

Then open http://127.0.0.1:8000/.
